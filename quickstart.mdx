This walkthrough produces a note from text, so you can exercise the complete
workflow before adding audio capture or file uploads.

## Before you begin

- Complete [sandbox onboarding](/sandbox) and [authentication](/authentication).
- Load the returned Partner JWT into `CORTEXA_JWT`. It needs `scribe:read`,
  `scribe:write`, and `scribe:generate`.
- The authorized clinician needs an available consult-note template and generation entitlement.
- Run the commands in the same Bash shell with cURL and `jq` available.

IDs and text returned below are illustrative. The commands capture your actual
IDs from responses, so later requests use the resources you created.

```bash
export CORTEXA_API_BASE='https://sandbox.api.cortexanote.com/v2/scribe/open-api'
export CORTEXA_DEMO_ID="demo-$(date -u +%Y%m%dT%H%M%SZ)"
```

The demo ID distinguishes this walkthrough from a later fresh run. Keep it and
all operation keys unchanged when retrying the current run.

## 1. Create a synthetic patient

```bash
patient_response=$(curl --fail-with-body --request POST "$CORTEXA_API_BASE/patients" \
  --header "Authorization: Bearer $CORTEXA_JWT" \
  --header 'Content-Type: application/json' \
  --data "$(jq -n --arg id "$CORTEXA_DEMO_ID-patient" \
    '{external_patient_id:$id,name:"Alex Example"}')")

export CORTEXA_PATIENT_ID=$(jq -r '.id' <<< "$patient_response")
```

The returned `id` is the Cortexa patient ID. Your external patient ID remains
available for lookup. Repeating creation with the same external ID returns the
existing patient within this grant.

## 2. Create the consultation

```bash
session_response=$(curl --fail-with-body --request POST "$CORTEXA_API_BASE/sessions" \
  --header "Authorization: Bearer $CORTEXA_JWT" \
  --header 'Content-Type: application/json' \
  --data "$(jq -n --arg id "$CORTEXA_DEMO_ID-visit" --arg patient "$CORTEXA_PATIENT_ID" \
    '{external_session_id:$id,patient_id:$patient,title:"Synthetic follow-up",background_context:"Synthetic consultation for integration testing.",output_language_code:"en"}')")

export CORTEXA_SESSION_ID=$(jq -r '.id' <<< "$session_response")
```

The session keeps this consultation's inputs and outputs together. See
[Sessions](/sessions) for optional language and template settings.

## 3. Submit the conversation

```bash
curl --fail-with-body --request POST "$CORTEXA_API_BASE/sessions/$CORTEXA_SESSION_ID/transcript/segments" \
  --header "Authorization: Bearer $CORTEXA_JWT" \
  --header 'Content-Type: application/json' \
  --header "Idempotency-Key: $CORTEXA_DEMO_ID-transcript-1" \
  --data '{"segments":[{"speaker":"clinician","text":"How has your sleep been since the last visit?"},{"speaker":"patient","text":"It has improved."},{"speaker":"clinician","text":"We discussed continuing the documented sleep routine and following up in four weeks."}],"language_code":"en","status":"completed"}'
```

The response includes the combined `full_text` and transcript `status`.
For a longer conversation, submit multiple [transcript batches](/transcripts).

## 4. Choose an available template

```bash
curl --fail-with-body "$CORTEXA_API_BASE/templates/consult-note-templates" \
  --header "Authorization: Bearer $CORTEXA_JWT"
```

Choose an ID from the returned `items`. Load it into `CORTEXA_TEMPLATE_ID`:

```bash
read -r -p 'Consult-note template ID: ' CORTEXA_TEMPLATE_ID
export CORTEXA_TEMPLATE_ID
```

If the list is empty, arrange template access with your integration contact.
Do not copy a template ID from another user's example.

## 5. Stream the note

```bash
curl --no-buffer --fail-with-body --request POST "$CORTEXA_API_BASE/sessions/$CORTEXA_SESSION_ID/consult-note" \
  --header "Authorization: Bearer $CORTEXA_JWT" \
  --header 'Content-Type: application/json' \
  --header 'Accept: text/event-stream' \
  --header "Idempotency-Key: $CORTEXA_DEMO_ID-note-1" \
  --data "$(jq -n --arg template "$CORTEXA_TEMPLATE_ID" \
    '{template_ids:[$template],output_language_code:"en"}')" \
  | tee ./cortexa-note-events.txt
```

The `200` response stays open while generation runs. You will see
`generation.started`, followed by text in `output.delta` events, and then an
`output.ready` event containing the saved document. No polling is needed.
Completed output may be returned immediately without deltas.

The local file contains the synthetic note. Use synthetic data for this example;
avoid saving clinical response bodies to ordinary logs in your integration.

## 6. Read the completed note

This example requested one template. Extract its final document from the saved
SSE events:

```bash
sed -n 's/^data: //p' ./cortexa-note-events.txt \
  | jq -s '[.[] | select(.document.status == "ready") | .document] | last' \
  > ./cortexa-note.json

jq -e '.id != null' ./cortexa-note.json
export CORTEXA_DOCUMENT_ID=$(jq -r '.id' ./cortexa-note.json)
jq -r '.rendered_text' ./cortexa-note.json
```

If no ready document was returned, handle the failure event or reconnect using
the same request and key. A closed stream alone is not success. The
[Streaming guide](/streaming) explains failures, reconnects, and the optional
`?stream=false` JSON mode for background integrations.

The final document includes `rendered_text`, structured `content`, `status`, and
`current_version`. Present the text for clinician review. To retain edits in
Cortexa, [save a versioned document update](/documents#save-an-edit). Use your own
EHR API to save the reviewed text into the mapped encounter.
